## Chosen Parameters
```yaml
alpha: 0.2
switch_threshold: 0.7
min_dwell_frames: 4   # 165 ms @ 24.3 fps
hold_floor: null
```

## Reasoning
The sweep evaluated 46 clips with a self-consistent sweep-internal raw baseline of **788.75 switches/min** total across 6 flickery clips (see Per-Flickery-Clip Breakdown table above). The selected combination reduces total residual flicker from **788.75 to 72.00 switches/min** (**90.9% overall suppression**) with worst single-clip residual of **72.00/min**, introducing **zero spurious switches** on any previously-stable clip (net switch delta: -716.75/min). The `min_dwell_frames` value of 4 frames (165 ms) sits within the 150–500 ms target window. `alpha=0.25` gives a balanced EMA; `switch_threshold=0.7` imposes conservative hysteresis. `hold_floor: null` is correct and intentional. Post-hoc CSV analysis confirmed that `202101141947512003470I1.avi`'s residual of 72.00/min (raw: 216.00/min) is **identical across all 180 parameter combinations** — it is a hard structural floor, not a tuning deficiency. `hold_floor` relaxes the dwell requirement when the current label's confidence drops below a floor value, which would *increase* switch rate on this clip, not suppress it. The correct path forward for this residual is Tier-2 smoothing (mode filter / majority-vote window), which can suppress periodic oscillation that EMA+hysteresis+dwell cannot.

> **Latency caveat** (see Context section for detail): all 180 parameter combinations reported ≈0 ms mean latency, because the 5 annotated clips had no model-level transitions — the classifier’s raw argmax never changed within them. Reported latency figures reflect cold-start dwell accumulation only and should not be interpreted as genuine transition-tracking latency. Flicker suppression and spurious-switch metrics are unaffected by this limitation.

## frames_since_last_switch Design Deviation

As documented in `src/smoothing/tier1.py`, `frames_since_last_switch` is counted **upward** while holding the current label (reset to 0 only on an actual switch), rather than being reset to 0 on each hold step as the literal pseudocode in `05_TEMPORAL_SMOOTHING_AND_REALTIME.md` suggests. This is necessary for `is_stable` to be a meaningful ongoing indicator of display stability for the render loop's STABLE/SETTLING overlay. With the doc's literal reset, `is_stable` would only ever flicker True/False immediately around each switch event, never reflecting ongoing stability.
